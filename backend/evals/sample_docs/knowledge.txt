Personal Knowledge Base — Architecture Overview

The Personal Knowledge Base is a self-hosted application that lets users ingest documents and query them using a Retrieval-Augmented Generation (RAG) pipeline. It is built with FastAPI for the HTTP layer, PostgreSQL for relational metadata, ChromaDB for vector storage, and LangGraph for orchestrating the chat pipeline.

Document Ingestion

Documents can be ingested in two ways: manual file upload and automated connector sync.

File uploads are accepted via a POST request to /api/collections/{collection_id}/documents. Supported formats are PDF, DOCX, and TXT. The raw file bytes are parsed into plain text using LangChain document loaders: PyPDFLoader for PDFs, Docx2txtLoader for Word documents, and TextLoader for plain text files.

Connectors are registered components that implement a BaseConnector interface. Each connector exposes an async generator called sync() that yields LangChain Document objects. A DummyConnector is provided for smoke testing. Connectors are registered at application startup and can be triggered via POST /api/connectors/{name}/sync.

Chunking Strategy

Parsed text is split using a two-level hierarchical chunking approach implemented with LangChain's RecursiveCharacterTextSplitter. Parent chunks are 3200 characters with no overlap, while child chunks are 800 characters with 80 characters of overlap. Child chunks are what gets embedded and stored in ChromaDB. Each chunk carries metadata including a parent_id, the full parent_text, the doc_id, and the collection_id. During retrieval, child chunks are used for similarity search but the larger parent text is returned to the language model, providing richer context.

Upsert Behaviour

When a document is re-uploaded or a connector re-syncs a previously seen source, the system performs a content-aware upsert. Each document row stores a source_uri (the filename or connector source path) and a SHA-256 content_hash of the parsed text. On ingest, the system looks up any existing document with the same (collection_id, source_uri). If the hash matches, ingestion is skipped entirely. If the hash differs, new chunks are written first, then the old document row and its ChromaDB chunks are deleted — ensuring the old version is never lost due to a failed re-ingest.

The Chat Pipeline

When a user sends a message, the application runs a five-node LangGraph state machine.

The collection_router node checks whether the target ChromaDB collection exists and contains documents. If it is empty or missing, it returns an early exit message without invoking the language model.

The query_rewriter node reformulates the user's question to be standalone. On the first message of a conversation it passes the question through unchanged. On follow-up messages it uses the language model to rewrite the question using the last six messages of history, optimising it for document retrieval.

The retriever node embeds the rewritten query and performs a nearest-neighbour search in ChromaDB, fetching the top ten results. Results are deduplicated by parent_id and the unique parent texts are passed forward.

The reranker node applies a cross-encoder model (cross-encoder/ms-marco-MiniLM-L-6-v2 from sentence-transformers) to score each query-chunk pair. The top five chunks by score are selected.

The generator node constructs a system prompt that instructs the language model to answer only using the provided context chunks. It appends the conversation history and the current user message, then streams the response token by token back to the client via Server-Sent Events.

Storage

PostgreSQL stores collections, documents, conversations, messages, and connector sync state. ChromaDB stores the vector embeddings and chunk metadata. The two stores are linked by the collection UUID, which is used as the ChromaDB collection name. Deleting a collection removes both the PostgreSQL row and the corresponding ChromaDB collection.
